# AI 실습·웹앱 진행 종합 보고서 v10

- **문서 성격:** 기존 진행 보고서 v1~v9와 개발 계획, 현재 저장소의 코드·산출물을 종합한 스냅샷
- **기준 기록:** 기존 실습 결과는 2026-10-09에 기록된 v9 및 사용자 공유 출력 기준
- **대상 프로젝트:** G-NAHPM-40 A100 MIG 40GB 오픈소스 AI 실습 및 로컬 AI Studio 개발 MVP
- **종합 상태:** 실습용 모델 파이프라인 0~6단계 데모 실행 완료. 통합 웹앱 코드가 구현되어 있으며 로컬 개발 실행 대상으로 준비됨. 운영 배포 승인을 의미하지 않음.
- **근거 구분:** 모델 실습 결과는 과거 사용자 공유 터미널 기록을 인용한다. 현재 저장소에서 확인 가능한 것은 코드·설정·산출물의 존재이며, 과거 실행을 이 보고서 작성 시점에 재현하거나 실제 GPU에서 다시 검증한 것은 아니다.

> v1~v9는 당시의 진행 기록으로 보존한다. 이후 변경은 새 버전으로 기록한다. 이 보고서는 이를 대체하지 않고 현황을 한곳에 모은 요약이다.

## 1. 요약

프로젝트는 환경 점검, Qwen2.5-14B 추론, vLLM API, 문서 RAG, Qwen2.5-7B QLoRA, API 벤치마크, Qwen2.5-VL 단일 이미지 처리까지 실습 파이프라인을 구성하고 데모 실행 결과를 남겼다. 현재 저장소에는 각 실습 코드와 통합형 AI Studio 웹앱(`apps/ai_studio/`)이 있다.

실습은 **파이프라인 동작 확인 수준의 proof-of-concept**이다. 작은 예제·단일 이미지 결과를 일반화 성능, 정책 정확도, 정산 정확도 또는 서비스 SLA로 해석할 수 없다. 웹앱도 인증·인가와 운영 통제가 부족한 로컬 개발 MVP이므로 `127.0.0.1`에만 바인딩하고 비민감·합성 데이터로만 사용해야 한다.

### 주요 측정치의 해석

- 5단계는 동시성마다 4건, 요청 최대 128 tokens의 작은 비스트리밍 표본이다. TTFT, 긴 시간 안정성, 운영 workload의 SLA를 측정하지 않았다.
- 4단계는 8개 학습 예시와 의미상 유사한 3개 평가 요청에 대한 좁은 category exact-match 결과다. 베이스/어댑터의 공정한 정량 비교나 일반화 성능 향상을 입증하지 않는다. 첫 사례 답변 기한도 5영업일과 7일로 달랐으며 정책 정답은 이 평가로 검증되지 않았다.
- 6단계는 한 이미지 출력의 JSON 형식과 출력 내부 합계만 점검했다. validation annotation에 필드 정답 텍스트가 없어 상호·날짜·금액·품목 정확도를 산출하지 않았다.

## 4. AI Studio 웹앱 현황

웹앱은 `apps/ai_studio/app.py`에서 FastAPI로 제공하며 정적 프론트엔드는 `apps/ai_studio/static/`에 있다. 화면에는 다음 기능 탭이 구성되어 있다.

1. **문서 도우미:** 기존 RAG 인덱스와 localhost vLLM API를 사용해 질문하고 출처를 보여주는 경로. 인덱스와 vLLM 서버가 별도로 준비되어야 한다.
2. **이미지 스튜디오:** FLUX.1-schnell 기반 텍스트-이미지 생성, SDXL Inpainting 기반 마스크 편집 작업 경로.
3. **동영상 생성:** 로컬 Wan2.2 저장소와 체크포인트가 설정될 때만 활성화되는 T2V/I2V 경로. 현재 설정 유무와 실제 GPU 실행 성공을 동일시하지 않는다.
4. **모델 실험실:** RAG 인덱싱, vLLM API 점검/벤치마크, 기본 추론, QLoRA 학습·평가, 분류 초안, VL 작업 제출 및 결과 다운로드 경로.

API에는 health/features 조회, 작업 제출·상태 확인·결과 제공이 구현되어 있다. 앱 내부 GPU 작업은 단일 worker/프로세스 내 lock으로 직렬화하지만, 별도 vLLM 프로세스나 다른 사용자의 GPU 작업과 조정하는 전역 GPU lease는 아니다.


실행 진입점은 `bash scripts/run_ai_studio.sh`이며 기본 주소는 `http://127.0.0.1:8080`이다. `scripts/run_ai_studio.sh`는 외부 인터페이스 바인딩을 거부하도록 작성되어 있다. 이 종합 작업에서 localhost 실행을 백그라운드로 시작했으나, 도구 측에서 프로세스의 최종 출력 및 `/api/health` 응답을 독립 확인하지 못했다. 따라서 URL은 실행 주소이며, 실제 브라우저 표시와 health 상태 확인을 운영체제에서 마무리해야 한다. 웹 UI 기동만으로 RAG/vLLM 또는 이미지·동영상 모델 실행 준비가 보장되는 것은 아니다.

상태 확인 예시: `curl -fsS http://127.0.0.1:8080/api/health` 및 `curl -fsS http://127.0.0.1:8080/api/features`.

## 5. 보안·운영 제한

현재 MVP에는 SSO, 사용자별 권한/문서 ACL, CSRF 방어, 악성 파일 검사, 다중 프로세스 GPU 스케줄링, 영속 job queue, 자동 보존·삭제 관리가 없다. 업로드와 결과는 로컬 작업 폴더에 남을 수 있고 job 상태는 메모리에 보관된다. 따라서:

- `127.0.0.1`에서만 실행하고 외부 네트워크에 직접 노출하지 않는다.
- 민감 문서, 실제 영수증, 개인정보 및 비밀정보를 입력하지 않는다.
- 별도 vLLM 서버가 GPU를 점유하는 동안 QLoRA/VL/미디어 생성 등 GPU 작업을 실행하지 않는다. GPU 상태를 수동 확인한다.
- 모델 최초 호출 시 모델 파일 다운로드·메모리 로딩이 발생할 수 있다. 모델 승인·라이선스·revision·캐시를 먼저 점검한다.
- 이미지 작업 원본·마스크·결과물의 자동 삭제를 전제로 하지 않는다. 테스트 후 생성된 작업 폴더를 확인해 직접 정리한다.
- 웹앱을 운영 서비스로 공개하기 전 SSO/RBAC, ACL 검색 필터, 업로드 검사, rate limit, 감사·보존·삭제, GPU lease/queue, 로그·모니터링, 백업/복구, 라이선스 및 보안 검토를 완료한다.

## 6. 남은 작업과 권고 순서

1. 웹앱 smoke test: `/api/health`, `/api/features`, 정적 화면 응답을 확인하고, vLLM/RAG 및 GPU 모델 의존성은 별도로 점검한다.
2. 문서 RAG 서비스화: 여러 문서 ingestion, 문서 버전·ACL, 근거 인용 검증, 답변 보류, 인덱스 교체·rollback과 권한 누출 테스트를 구현한다.
3. 인증·데이터 거버넌스: 대상 사용자와 문서 owner, SSO/RBAC, 개인정보 등급, 보존·삭제 기간, 로그 정책을 정한다.
4. 품질 검증: 독립 RAG 평가셋, 분류 held-out 데이터, VL 필드 정답 데이터와 사람 검토 기준을 준비한다. 기존 데모 점수를 출시 기준으로 재사용하지 않는다.
5. GPU 운영: 전역 job lease, 큐 상한/취소, 외부 프로세스와 자원 조율, capacity·OOM·장시간 안정성 시험을 설계한다.
6. 이미지·동영상 기능은 승인된 모델 revision과 라이선스를 고정하고 MIG에서 peak VRAM·실행시간·실패율을 단독 측정한다.
7. 제한 파일럿 전 업무 owner, 보안·개인정보 담당자, 운영 담당자의 명시적 승인을 받는다. 자동 결재·지급·보안 조치는 별도 사람 승인 없이 수행하지 않는다.

## 7. 결론

현재까지의 결과는 교육용 AI pipeline 및 통합 웹앱 UI/API의 proof-of-concept을 구성하고, 제한된 입력에서 일부 end-to-end 실행을 확인한 상태다. 앱 개발을 이어갈 기반은 마련되어 있으나 문서 ACL·SSO·운영 큐·독립 품질 평가·데이터 보존과 실제 MIG 운영 검증이 남아 있다. 그러므로 **로컬 개발 MVP 단계**로 분류하며, 실서비스 투입 가능 또는 모델의 업무 정확성이 입증되었다고 판단하지 않는다.
